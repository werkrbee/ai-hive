# Outcome brief

Use this structure for a planning handoff. Keep answers short; omit irrelevant
fields and write "unknown" where evidence is missing. Attach supplied sources
or context references to factual claims. Do not persist customer information
outside the user's authorized destination.

| Field | Capture |
|-------|---------|
| User and situation | Who experiences the problem and when |
| Job to accomplish | What they need to do, independent of a proposed solution |
| Current approach and friction | Existing workaround, observed failure, and evidence |
| Desired outcome | The observable change that would help |
| Success measure | Metric, baseline, target, time window, and measurement source; label proposals |
| Constraints | Explicit requirements, budget, privacy, timing, and dependencies |
| Options | Smallest intervention, existing capability/process, and tradeoffs |
| Recommendation | Selected approach and its connection to the need |
| Acceptance criteria | Observable checks for the selected approach and intended outcome |
| Unknowns and validation | Assumptions, unresolved questions, and the next low-cost check |

Distinguish implementation acceptance from outcome validation. A working alert
can pass a functional check without proving it reduces recovery time. Record both
when the outcome needs observation after delivery; never claim benefit solely
because a feature shipped.
